# Auth: Design Spec

- **Date:** 2026-09-17
- **Status:** Approved in chat, pending written review
- **Scope:** database layer (Postgres + Drizzle) and full-stack authentication (Express API + React client)

## 1. Goals

- Users can register, log in, stay logged in across page reloads, and log out.
- Two roles: `user` and `admin`. The server enforces admin-only routes, and the client hides admin UI from non-admins.
- Use the JWT access token + rotating refresh token pattern (the one used in the owner's work stack), so the owner learns how it works end to end.
- Keep the code readable. It is study material.

### Non-goals (for now)
Password reset, email verification, OAuth/social login, "remember me", account lockout, a cap on token family lifetime, and an admin UI for managing users.

## 2. Infrastructure

- **`docker-compose.yml`** (repo root) runs the `postgres:17` service.
  - Host port **5433** maps to container port 5432, because 5432 is taken on the dev machine.
  - Data lives in the named volume `pgdata`.
  - An init script creates two databases: `interview_prep` (dev) and `interview_prep_test` (tests).
- **`server/.env`** (gitignored) holds the variables below. `server/.env.example` is committed and documents them.

  | Variable | Example / rule |
  |---|---|
  | `NODE_ENV` | `development` \| `test` \| `production` |
  | `PORT` | default `4000` |
  | `DATABASE_URL` | `postgres://app:app@localhost:5433/interview_prep` |
  | `JWT_ACCESS_SECRET` | at least 32 characters |
  | `ADMIN_EMAIL`, `ADMIN_PASSWORD` | used only by the seed script |

- **`server/src/config.ts`** validates `process.env` with Zod at startup. If validation fails, the process exits with a readable list of problems. The rest of the code imports the typed `config` object and never reads `process.env` directly.

## 3. Data model (Drizzle, `server/src/db/schema.ts`)

### `users`
| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | `defaultRandom()` |
| `email` | text, unique, not null | stored trimmed and lowercased |
| `password_hash` | text, not null | scrypt format, see §5 |
| `role` | pg enum `user_role` (`user`, `admin`) | default `user` |
| `created_at` | timestamptz | default `now()` |

### `refresh_tokens`
| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK → `users.id` | `on delete cascade`, indexed |
| `token_hash` | text, unique, not null | SHA-256 hex of the raw token. The raw token is never stored. |
| `family_id` | uuid, not null, indexed | Every token descended from one login shares a family. |
| `expires_at` | timestamptz, not null | |
| `revoked_at` | timestamptz, null | |
| `replaced_by` | uuid, null | id of the token that replaced this one |
| `created_at` | timestamptz | default `now()` |

- Migrations are generated by `drizzle-kit generate` into `server/drizzle/` as `.sql` files, committed to git, and applied with `drizzle-kit migrate`.

## 4. API

All auth routes live under `/api/auth`. JSON in, JSON out.

| Method | Path | Auth | Request | Success response |
|---|---|---|---|---|
| POST | `/register` | none (rate-limited) | `{ email, password }` | `201 { accessToken, user }` + sets cookie |
| POST | `/login` | none (rate-limited) | `{ email, password }` | `200 { accessToken, user }` + sets cookie |
| POST | `/refresh` | `ip_refresh` cookie | none | `200 { accessToken, user }` + sets rotated cookie |
| POST | `/logout` | `ip_refresh` cookie (optional) | none | `204` + clears cookie |
| GET | `/me` | Bearer | none | `200 { user }` |
| GET | `/api/admin/ping` | Bearer + role `admin` | none | `200 { ok: true }` |

- **Public user shape:** `{ id, email, role, createdAt }`. It never includes `password_hash`.
- **Error format:** `{ error: { code, message, details? } }`

| Status | code | When |
|---|---|---|
| 400 | `VALIDATION_ERROR` | invalid body or params; `details` is `z.flattenError(err).fieldErrors`, i.e. `Record<field, string[]>` |
| 401 | `INVALID_CREDENTIALS` | wrong email or password (same message for both) |
| 401 | `UNAUTHENTICATED` | missing, invalid or expired access token |
| 401 | `INVALID_REFRESH_TOKEN` | missing, unknown, expired or reused refresh token |
| 403 | `FORBIDDEN` | authenticated, but wrong role |
| 404 | `NOT_FOUND` | the resource doesn't exist (shared by all features) |
| 409 | `EMAIL_TAKEN` | register with an existing email |
| 429 | `RATE_LIMITED` | too many login/register attempts |
| 500 | `INTERNAL_ERROR` | anything unexpected; no stack trace in the response, full error logged on the server |

- **Validation:**
  - `email`: trimmed, lowercased, valid email format, max 254 characters.
  - `password`: 8–128 characters.

## 5. Security mechanics

### Passwords (`auth/password.ts`)
- Hashed with Node's `crypto.scrypt`: random 16-byte salt, 64-byte key, parameters `N=16384, r=8, p=1`.
- Stored as `scrypt$N$r$p$<saltB64>$<hashB64>`, so the parameters can be changed later without breaking existing hashes.
- Verified with `crypto.timingSafeEqual`.
- When a login email does not exist, the server still verifies the password against a fixed dummy hash, so response timing doesn't reveal whether the email is registered.

### Access token (`auth/tokens.ts`)
- JWT made with `jose`: HS256, `JWT_ACCESS_SECRET`, TTL 15 minutes.
- Claims: `sub` (user id), `role`, `iat`, `exp`.
- **Known trade-off:** access tokens are stateless, so they stay valid until they expire (at most 15 minutes), even after logout or a role change.

### Refresh token
- Raw value: `crypto.randomBytes(32)`, base64url-encoded. TTL 7 days.
- The database stores only its SHA-256 hash.
- Cookie settings:
  - name `ip_refresh`
  - `httpOnly: true`
  - `sameSite: 'strict'`
  - `secure: NODE_ENV === 'production'`
  - `path: '/api/auth'`
  - `maxAge`: 7 days
- **Known trade-off:** if a refresh response is lost after the server rotated the token (tab closed or reloaded mid-request), the browser keeps the old cookie, the next refresh looks like reuse, and the user is logged out. A short reuse grace window could soften this later (not implemented).

### Login / register
- On success, a new `family_id` is created, the first refresh token is inserted, and the response returns the access token and user.

### Refresh algorithm (`auth.service.ts → refresh(rawToken)`)
1. No token, or no row matches its hash → `INVALID_REFRESH_TOKEN`.
2. Otherwise, in a single transaction:
   - Lock the user's row first (`SELECT … FROM users … FOR UPDATE`) — refresh and logout both do this, so reuse revocation can't miss a token a parallel refresh is inserting.
   - Lock the token row with `SELECT … FOR UPDATE`.
   - Row has `revoked_at` set → **reuse detected**: revoke every non-revoked token in `family_id`. This revocation happens inside the same transaction, so it commits even though the request still ends in an error.
   - `expires_at` is in the past → invalid.
   - Otherwise: insert the new token (same family, fresh 7-day expiry), set `revoked_at = now()` and `replaced_by = new.id` on the old token, and load the user.
3. Outside the transaction: reuse → log a warning and return `INVALID_REFRESH_TOKEN`; invalid → return `INVALID_REFRESH_TOKEN`; otherwise return `{ accessToken, user }` plus the new raw refresh token.

### Logout
- Takes the same user-row lock as refresh before touching tokens.
- If a cookie is present and matches a row, revoke all tokens in that family.
- Always clear the cookie and return 204.

### Middleware
- **`requireAuth`:** parses `Authorization: Bearer <jwt>`, verifies it, and sets `req.user = { id, role }`. Any failure returns `UNAUTHENTICATED`.
- **`requireRole(...roles)`:** must run after `requireAuth`. A role not in the list returns `FORBIDDEN`.
- **`errorHandler`:** maps `AppError(status, code, message)` and `ZodError` to the error format above. Anything else becomes a 500.
- **`server/src/lib/errors.ts`:** defines the `AppError` class and the `ErrorCode` union type. New features add their error codes to that union.
- **`server/src/db/client.ts`:** exports `db`, using the `pg` driver (`drizzle-orm/node-postgres`).
- **`isUniqueViolation(err)`** (in `lib/errors.ts`): detects Postgres error `23505`, including when Drizzle wraps it in `err.cause`.
- **Middleware files:** `server/src/middleware/requireAuth.ts`, `requireRole.ts` and `errorHandler.ts`.

### Hardening
- `helmet()` sets security headers; `X-Powered-By` is removed.
- `express-rate-limit` on `/login` and `/register`: 10 requests per 15 minutes per IP. It is disabled when `NODE_ENV=test`.
- **CSRF:**
  - Only `/refresh` and `/logout` authenticate by cookie. `SameSite=Strict` stops cross-site requests from carrying the cookie.
  - All other protected routes require the Bearer header, which browsers never attach automatically.

## 6. Seed script

- `npm run db:seed-admin -w @app/server` creates or updates the user `ADMIN_EMAIL`, sets role `admin`, and sets the password from `ADMIN_PASSWORD`.
- The script is idempotent: running it again changes nothing.
- The API offers no way to become admin.

## 7. Client

### Dependencies
- `react-router` (declarative mode).
- **Dev dependencies:** `vitest`, `@testing-library/react`, `@testing-library/user-event`, `jsdom`.
- **Test setup:** `client/src/test/setup.ts` runs `cleanup()` and `vi.restoreAllMocks()` after each test. Vitest globals are off, and `jest-dom` isn't used.
- No UI library. Forms are plain controlled inputs.

### `api/client.ts`
- **Token storage:** a module-level `let accessToken: string | null`, with `setAccessToken` and `getAccessToken`.
- **`apiFetch<T>(path, options)`:**
  - Adds JSON headers, plus `Authorization` when a token exists.
  - Parses the error format and throws `ApiError { status, code, message, details }`.
- **On a 401 from a non-auth endpoint:**
  - Calls `refreshAccessToken()`, then retries the original request **once**.
  - If the refresh fails, clears the token, emits `authLost`, and rethrows.
- **`refreshAccessToken()`, single-flight:**
  - Concurrent callers share one in-flight promise.
  - Inside it, the actual request runs within `navigator.locks.request('auth-refresh', …)`, so separate tabs refresh one at a time and each sends the newest cookie. Falls back to no lock if `navigator.locks` is unavailable.
- **`onAuthLost(listener)`:** subscribe/unsubscribe for the "auth lost" event.
- **Excluded from the retry logic:** `/api/auth/login`, `/register`, `/refresh` and `/logout`.

### `api/auth.ts`
- Typed wrappers: `login`, `register`, `logout`, `refresh`, `getMe`.
- `login`, `register` and `refresh` store the returned access token.
- `logout` clears it.

### `auth/AuthProvider.tsx` and `auth/useAuth.ts`
- **State:** `{ user: User | null, status: 'loading' | 'authed' | 'guest' }`.
- **On mount:** calls `refresh()`. Success → `authed`; failure → `guest`.
- **Exposes:** `login`, `register` and `logout`, each updating state.
- Subscribes to `onAuthLost` and switches to `guest`.

### `auth/RequireAuth.tsx`
- Props: `{ roles?: Role[], children }`.
- `loading` → shows a spinner.
- `guest` → `<Navigate to="/login" state={{ from: location }} replace />`.
- Role not allowed → renders a Forbidden message.

### Routes (`App.tsx`), all inside `components/Layout.tsx`
| Path | Page | Guard |
|---|---|---|
| `/` | Home: keeps the hello-world check | none |
| `/login`, `/register` | forms that show server errors; on success go to `from` or `/`; an already-authed user is redirected to `/` | none |
| `/profile` | shows `user` from `getMe()` | `RequireAuth` |
| `/admin` | calls `/api/admin/ping` and shows the result | `RequireAuth roles={['admin']}` |
| `*` | NotFound | none |

### Layout navigation
- Guests see Login and Register.
- Authed users see their email, Profile and Logout.
- Admins also see an Admin link.

## 8. Testing (Vitest)

### Server (`server/test/`)
- Supertest against `app`, using `DATABASE_URL` pointed at `interview_prep_test`.
- Migrations run once in global setup.
- Before each test, every table in the `public` schema is truncated. The list of tables is read from the database, so new tables need no test changes.
- **`server/test/helpers.ts`:** `createUserWithToken({ role })` creates the user through the service, sets the role, logs in, and returns `{ user, accessToken }`.
- **`password.test.ts`:** a hash verifies; a wrong password fails; two hashes of the same password differ.
- **`tokens.test.ts`:** sign then verify round-trips; a tampered token is rejected; an expired token is rejected.
- **`auth.routes.test.ts`:**
  - register returns 201 and sets the cookie; a duplicate returns 409; an invalid body returns 400
  - login with a wrong password or unknown email returns 401 with the same message
  - `/me` without a token returns 401; with a valid token returns 200
  - `/refresh` returns a new cookie that differs from the old one, and the old token's row is revoked
  - reusing an old refresh token returns 401, and the new token from the same family also stops working
  - logout returns 204, and a refresh afterwards returns 401
  - `/api/admin/ping` returns 403 for a `user` and 200 for an `admin`

### Client (`client/src/api/client.test.ts`)
- Mocked `fetch`: three concurrent calls get a 401 → exactly **one** refresh request → all three retried and resolved.
- A failed refresh → `authLost` is emitted and the callers reject.
- A 401 from `/api/auth/login` does not trigger a refresh.

### Manual check
- In the running app: register → reload (still logged in) → profile → logout → admin guard, checked both as a user and as the seeded admin.

### Environment loading
- **Dev scripts** (`dev`, `db:seed-admin`) load `server/.env` with Node's built-in `--env-file` flag, so no `dotenv` dependency is needed.
- **`drizzle.config.ts`** loads it with `process.loadEnvFile()` (built into Node), because drizzle-kit is not started through a Node flag.
- **Tests** don't read `.env`. `server/vitest.config.ts` sets `test.env`:
  - `NODE_ENV=test`
  - the test `DATABASE_URL` (the `interview_prep_test` database)
  - a fixed test-only `JWT_ACCESS_SECRET`

  This means tests work with no secrets present.
- **Setup:** the owner creates `server/.env` from `.env.example`. Claude Code's project settings deny it read and write access to `.env` files.
